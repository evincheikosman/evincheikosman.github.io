Q — AI Routine & Playlist Builder

Built solo, outside of work, with no engineering team or org behind it

An AI-powered routine and playlist builder for Lagree fitness instructors — I'm a certified instructor myself, and Q replaces the 30–45 minutes of manual class-sequencing and playlist-building I used to do before every session.

Role Solo — product, design & full-stack build
Stack Next.js, TypeScript, Claude API, Supabase
Status Live in production, testing with real users
Live q-app-delta.vercel.app ↗

⚠ The Problem

Before every Lagree class I teach, I was doing the same manual work: sequencing a full ~40-minute routine by hand, exercise by exercise — spring loads, platform facing, timing, cues — and separately building a playlist that actually matched the energy arc I wanted the class to have. It happens before you even walk in the door, every single time, and none of it requires a human once the pattern is clear. I wanted to see if I could build the tool myself, entirely outside of work, with no engineering background beyond what I'd taught myself at Meta.

⚙ What I Built

A full-stack Next.js app I designed, built, and shipped alone — from the AI generation logic through to a real-time multi-user backend. Unlike the internal tools I built at Meta, there was no existing user base, no stakeholders, and no engineering team to lean on — every architectural decision was mine to make and live with, down to deploying on Vercel so I could ship a change and put a working URL in front of real instructors within minutes.

  • AI routine builder — instructor describes focus areas, energy arc, class level, and vibe; Claude generates a complete routine with ordered exercises, spring loads, timing, and instructor cues, tuned to a defined difficulty contract per energy arc
  • AI playlist curation — maps a requested artist anchor to a BPM-matched, DJ-style playlist via the Spotify API, tuned to avoid over-indexing on a single artist
  • Teach Mode — a glanceable, auto-advancing single-screen view of the current move, spring load, and countdown for use mid-class
  • Your Cue — reflects patterns in an instructor's own teaching data (top artists, recurring emphasis, energy arcs) back to them once there's enough history to say something real
  • Real per-user personalization — every device gets its own private profile, teaching schedule, and library; nothing is hardcoded to me
  • Real-time multi-user layer — anonymous accounts, invite-code friend connections, and live 1:1 messaging with routine/playlist sharing, backed by Postgres Row Level Security
  • Progressive Web App — installable on iOS/Android home screens, full offline-capable single-device core

◎ Technical Integrations

  • Anthropic Claude API — structured prompt engineering for routine generation and playlist curation, including a difficulty-contract system that ties an instructor's chosen energy arc to concrete move selection and progression rules
  • Spotify Web API + NextAuth.js — OAuth with automatic token refresh, playlist creation, track search and BPM/audio-feature filtering
  • Supabase (Postgres + Row Level Security + Realtime) — anonymous authentication, a friend-connection graph, and live-delivered direct messages, scoped narrowly so the rest of the app stays fully functional with zero backend configured
  • Claude Code — used throughout for implementation, debugging, and iterating on both the product and the underlying AI prompt design

✦ What I Learned

Building Q was a different kind of test than the tools I built at Meta. There, I had a captive, motivated user base and a clear org problem to solve. Here, I had to make every product call myself — including the ones with no obvious right answer, like how to design a friend-connection model that's simple enough for a fitness instructor to use in ten seconds but secure enough to trust with real people's data.

The most instructive part was debugging the multi-user layer once real people started using it. Two friends couldn't connect to each other on the first try — the fix required understanding exactly how Postgres Row Level Security evaluates a query before the row it's protecting has been created, and designing a narrowly-scoped bypass instead of loosening security broadly. That's the kind of judgment call that only shows up once real users hit the system in ways you didn't script for.
